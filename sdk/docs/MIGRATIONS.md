# Foundation SDK — migration guide

This document ships with the SDK. It holds **one chapter per SDK release worth migrating to**: each chapter presents that release's app model, then gives a migration path from every starting state met in the field. New chapters are added as new releases ship (a 1.x.x → 2.x.x chapter will join this one), so the ladder from any old app to the current SDK stays in one file.

Chapters:

- **Migrating to SDK 1.0.0** (below) — from SDK 0.4.0 apps, interim dev-bundle apps, in-tree KeyOS apps, apps using OS surfaces the SDK doesn't expose yet, or code that never compiled at all.

---

# Migrating to SDK 1.0.0

## The 1.0.0 app model (the target)

An SDK 1.0.0 app is a standalone Cargo project generated by `foundation new`:

- **Entry**: `app_ui2!("<app-name>")` + `fn app_main(cx: AppContext, ui: AppWindow)`; UI in `ui/app.slint` (plus optional router pages), callbacks in `ui/callbacks.slint` (§5).
- **SDK linkage**: path dependencies through an app-local `.foundation-sdk/current` symlink that survives SDK updates — no absolute versioned paths (§3).
- **Theming**: `resources/theme.json` compiled by the CLI, `include_theme!`/`apply_theme!` in `src/theme.rs`, visual editor via `foundation theme` (§6).
- **Permissions**: `app-config.toml` `[permissions]` + `permission_templates.toml`, resolved against per-message policy metadata — grantability comes from permission groups, and some messages are Foundation-signed-only (§7).
- **Assets**: a committed `resources/` tree; a 110×110 transparent-glyph launcher icon, with an optional `-dark` sibling (gotcha 11).
- **Workflow**: `foundation doctor` → `preview` → `sim` → `build`/`sideload` → `pack` for a single-file `.app` distribution archive (§10).

## Which migration path applies

Whatever the starting state, the destination is the same fresh scaffold — port into it rather than patching in place (§2). What varies is how much of this chapter applies:

| Your starting state | Fingerprint | Path |
|---|---|---|
| **SDK 0.4.0 app** | `app_ui!`, absolute versioned SDK paths, `theme/theme.json` + build-script theme compilation | The main path: §2 scaffold, then the §3–§10 diffs |
| **Interim dev-bundle app** | `app_minimal!` (a macro that exists in no packaged SDK), git-pinned KeyOS deps or absolute `sdk/current` paths | Same as 0.4.0 (§2–§10); the entry-macro step is §5 |
| **In-tree KeyOS app** | `app!`, `{ workspace = true }` deps, `manifest.toml` only, built by `cargo xtask` inside a KeyOS checkout | §2 scaffold, then §13 (compat-shim for the in-tree `@ui` widget surface) on top of §3–§10 |
| **App using an OS surface the SDK doesn't expose** (the USB vendor interface is the clearest case) | transport imports with no matching SDK crate or service manifest | Whichever row above fits, plus §14 (feature-gate + mock the missing surface) |
| **App whose transport is shipped but signature-gated** (BLE, QuantumLink) | the crate resolves, but §7.3 says the messages it needs are Foundation-only | Whichever row above fits, plus §14 for the same gate-and-stub remedy, with the §7.3 diagnosis: the block is a signature, not a missing dep |
| **Code that never compiled against any real SDK** (e.g. AI-generated against imagined APIs) | dependencies and service/permission names that exist in no SDK; `no_std` mixed with a plain `fn main` | Treat as new development: §2 scaffold, keep the protocol/data types and the UX design, rewrite the platform layer against §3–§10 (and §14 for missing transports) |

The 0.4.0 → 1.0.0 material below was produced by diffing the two installed SDK bundles — the app templates, the `foundation` CLI, every `lib/keyos` crate an app links against, the `@ui` Slint widget library, and apps generated with both CLIs. Neither bundle ships a changelog; this chapter fills that gap.

## 1. At a glance: 0.4.0 → 1.0.0

| | SDK 0.4.0 | SDK 1.0.0 |
|---|---|---|
| Slint toolkit | v1.12.1-foundation8 | v1.17.0-foundation2 (declares `rust-version = "1.92"`) |
| Rust toolchain (dev shell) | nightly-2025-09-11, xous std 1.91.0 | nightly-2026-04-11, xous std 1.96.0 |
| nixpkgs | nixos-24.11 | nixos-26.05 |
| Service API crates | 9 | 12 (adds **backup, camera, nfc, security**; drops bt) |
| Total service messages | 208 | 292 |
| CLI commands | 13 | 16 (adds **clean, pack, theme, themes**; drops `view`, folded into `preview`) |
| Bundled tools | 5 | 10 (adds asset-tool, theme-compiler, theme-editor, fatfs-image, passport-drive) |
| Templates | default-app, multi-page-app | + **kitchen-sink** (component/theme gallery) |
| App → SDK linkage | absolute versioned paths in Cargo.toml | app-local `.foundation-sdk/current` symlink |

**The three big reworks** you will definitely touch:

1. **Entry macro**: `app_ui!` is *removed* (not deprecated). Use `app_ui2!`.
2. **Theming**: build-script theme compilation + ~200 lines of hand-written token plumbing are replaced by CLI-generated themes, `include_theme!` / `apply_theme!`, and a visual editor (`foundation theme`).
3. **SDK path handling**: apps no longer hardcode `/home/…/foundation-sdk-0.4.0-…` paths; they reference `.foundation-sdk/current`, which survives SDK updates.

**What did *not* change** (port as-is): the `fn app_main(cx: AppContext, ui: AppWindow)` entry point and `ui.run()`; the router/multi-page pattern (`ui/pages/<name>/{page,props}.slint`, `@rust-attr(route(path = "/…"))`, `Navigate.*`, `include_router: true`); `ui/callbacks.slint`; the `i18n/<locale>.json` format and `tr` surface; `permission_templates.toml` syntax and `[permissions] template = […]` expansion; the `#[derive(Server)]` / `#[derive(Permissions)]` / `#[derive(Message)]` macros; `subscribe_scalar` and the worker/executor APIs (`spawn`, `spawn_local`, `sleep`, `timeout`, …); all 29 `@ui` component names (but see §4.4 — some component *APIs* changed, e.g. `Dialog`); the core `app-config.toml` keys.

## 2. Recommended migration path

Port into a freshly generated app rather than patching in place — the skeleton changes (`.foundation-sdk`, `AGENTS.md`, theme pipeline, gitignore) come for free that way.

```sh
# 1. Verify the 1.0.0 environment
foundation doctor

# 2. Generate the new app (flags are new in 1.0.0; 0.4.0 only had -t/--no-git and prompted for the rest)
# --template:    or multi-page-app / kitchen-sink
# --app-id:      REUSE your 0.4.0 app-id to stay the same app
# --app-version: BUMP vs the original (e.g. 0.4.0 app was 0.1.0 → port is 0.2.0)
foundation new my-app \
  --template default-app \
  --friendly-name "My App" \
  --launcher-name "MyApp" \
  --description "…" \
  --publisher-name "…" \
  --contact-email "…" \
  --support-url "https://…" \
  --app-id 0xYOUR_EXISTING_APP_ID \
  --app-version 0.2.0 \
  --min-keyos-version 1.0.0
```

**The app-id is also the domain-separation input to `GetAppSeed`** (`hmac256(app_id, master_seed)`), so it is not just install identity: change the app-id and every app-seed-derived key rotates with it, unrecoverably. Since gotcha 21 tells you to re-root your derivation in the app seed, treat the app-id as key material from here on.

Pass your existing `app-id` so the device treats the migrated app as the same identity — but **bump the version**: the port must carry a version higher than the last 0.4.0 release (original `0.1.0` → port `0.2.0`), both in `app-config.toml` (`--app-version` / `version`) and in the crate `version` of `Cargo.toml`, so a sideload upgrades the installed original cleanly and the two builds are distinguishable in logs.

**The publisher key is the other half of install identity.** A `.app` installed from Settings over an existing app is an update only when the same publisher key signed both; the new bundle is staged and swapped in whole, so an archive that fails to unpack costs the user nothing. Install checks the signed manifest and that the archive carries exactly the files it hashes, not the contents of those files: a bundle whose payload does not match its `fileHashes` installs and is refused at launch instead. The same app-id under a *different* key is refused (Settings reports it as installed from another publisher) until the user removes the installed app, and removal wipes that app's AppData and granted permissions with it. A running app is likewise refused until closed. So keep the signing identity as stable across releases as the app-id: rotating it turns every user's next update into a remove-and-reinstall that loses their data and grants.

Then port files:

| 0.4.0 file | Action in the 1.0.0 app |
|---|---|
| `app-config.toml` | Regenerate; copy over custom `[permissions]` entries. New `theme = "resources/theme.json"` key is already present. |
| `permission_templates.toml` | **Do not copy.** Start from the new template and re-add your custom templates (see §7). |
| `Cargo.toml` | Keep the generated one; re-add your extra `[dependencies]` (see §3). |
| `build.rs` | Keep the generated one; re-apply custom `CompileOptions` fields (`include_router`, `include_translations`, …). |
| `src/main.rs` | Copy yours, then apply the `app_ui2!` change (§5). |
| `src/theme.rs` | **Do not copy.** Keep the generated one; move any custom overrides into `apply_system_theme()` after `apply_theme!` (§6). |
| `src/*` (your modules) | Copy; fix service-API breakages (§8–§9). |
| `theme/theme.json` | Move to `resources/theme.json` (§6). |
| `ui/app.slint`, `ui/pages/**` | Copy; fix `@ui/theme.slint` imports and button sizes (§4). |
| `ui/callbacks.slint` | Copy unchanged. |
| `i18n/*.json` | Copy unchanged. |
| `resources/icon.svg` | Copy — **must be exactly 110×110 px** (1.0.0 hard-errors otherwise) and should be a **transparent-background glyph**: the launcher supplies the ring-and-disc badge itself. An optional dark-theme variant ships as a `<stem>-dark.*` sibling (gotcha 11). |
| loose image/font assets | Move images to `resources/images/`, fonts to `resources/fonts/` (§4.2). ⚠️ 0.4.0's gitignore wrongly swallowed `resources` — check every `@image-url` in the UI actually resolves to a file in the repo; assets lost that way must be recreated. |
| `.gitignore` | Keep the generated one (`target/`, `.foundation-sdk/`, `ui/ui`, `manifest.toml`; note 0.4.0 wrongly ignored `resources` — in 1.0.0 `resources/` **must be committed**). |

Then iterate with the workflow ladder: `foundation preview ui/app.slint` (UI only) → `foundation sim` (hosted runtime) → `foundation build` / `foundation sideload` (hardware) → `foundation pack` (a single `.app` file for distribution — installable on-device from Settings > Apps > Install App).

## 3. Project structure, Cargo.toml, build.rs

### 3.1 SDK reference: `.foundation-sdk/current`

0.4.0 `foundation new` wrote **absolute, versioned** paths:

```toml
server = { path = "/home/you/.foundation/sdk/foundation-sdk-0.4.0-x86_64-unknown-linux-gnu/lib/keyos/server" }
```

1.0.0 creates a hidden `.foundation-sdk/current` symlink → `~/.foundation/sdk/current` and references everything through it:

```toml
[workspace]
exclude = [".foundation-sdk"]

[dependencies]
log = "0.4"
log-server = { package = "xous-api-log", path = ".foundation-sdk/current/lib/keyos/xous/api/log" }
server = { path = ".foundation-sdk/current/lib/keyos/server" }
slint-keyos-platform = { path = ".foundation-sdk/current/lib/keyos/slint-keyos-platform/runtime" }
foundation-themes = { path = ".foundation-sdk/current/lib/keyos/sdk/crates/foundation-themes" }

[build-dependencies]
slint-keyos-platform-build = { path = ".foundation-sdk/current/lib/keyos/slint-keyos-platform/build" }

# Randomness is pre-wired: add `getrandom = "0.2"` (or `rand = "0.8"`) and calls
# route to the TRNG on device. Stay on the getrandom 0.2 line; 0.3+ is uncovered.
[patch.crates-io]
getrandom = { path = ".foundation-sdk/current/lib/keyos/imports/getrandom" }
```

Differences from 0.4.0 besides the paths:

- `[workspace] exclude = [".foundation-sdk"]` — required so Cargo doesn't treat the SDK checkout as workspace members.
- `foundation-themes` is **dropped from `[build-dependencies]`** (theme compilation left the build script).
- New `[patch.crates-io] getrandom` — `getrandom` 0.2 / `rand` 0.8 in your dependency tree route to the hardware TRNG on device. Stay on the 0.2 line; 0.3+ is not covered by the patch.
- Dependency *names* are unchanged, so your `use` statements keep working.

**If your app has a member crate (`*-core`), do NOT add an explicit `[workspace] members` list.** In 0.4.0 the SDK was referenced by an *outside* path (`../keyos-sdk/…`), so an app workspace could safely say `members = [".", "my-core"]`. In 1.0.0 the SDK is reached through the **`.foundation-sdk` symlink inside the project directory**, and an explicit `members` list makes Cargo pull those symlinked SDK crates into *your* workspace — they then fail to inherit `slint` from their own (SDK) workspace root:

```
error: failed to load manifest for dependency `foundation-themes`
  … failed to parse manifest at `.../.foundation-sdk/current/lib/keyos/ui2/components/Cargo.toml`
  … error inheriting `slint` from workspace root manifest's `workspace.dependencies.slint`
  … `workspace.dependencies` was not defined
```

The fix is to keep only `exclude = [".foundation-sdk"]` and let the member crate be an **implicit** member — a path dependency living inside the project directory is picked up automatically:

```toml
[workspace]
exclude = [".foundation-sdk"]

[dependencies]
my-core = { path = "my-core" }   # implicit workspace member — no `members` list
```

Single-package apps never hit this; it only appears once you port an app that carries a `*-core` (or similar) sub-crate.

**Remove any `[patch.crates-io]` pins to a specific Slint fork.** Some apps pinned the whole Slint stack to the bundle they were built against, e.g.:

```toml
[patch.crates-io]
slint      = { git = "https://github.com/Foundation-Devices/slint.git", tag = "v1.12.1-foundation11" }
slint-build = { git = "…", tag = "v1.12.1-foundation11" }
i-slint-core = { git = "…", tag = "v1.12.1-foundation11" }   # …and i-slint-compiler / -common / -backend-winit
```

1.0.0's `slint-keyos-platform` depends on Slint **v1.17.0-foundation2**; leaving the old `v1.12.1` pins in place forces a conflicting second Slint version into the graph and the build fails to resolve. Delete the whole block (keep only the `getrandom` patch). The SDK supplies Slint transitively — apps don't pin it.

**Apps with a two-target `[dependencies]` split (host-sim vs device) port each side independently.** Apps that run both in the hosted simulator and on hardware often split dependencies by target:

```toml
[target.'cfg(not(target_os = "xous"))'.dependencies]   # host / simulator transport
tokio = { … }
tokio-tungstenite = "0.24"

[target.'cfg(target_os = "xous")'.dependencies]         # device-only
p256 = "0.13"
security = { path = ".foundation-sdk/current/lib/keyos/api/security" }
usb = { path = ".foundation-sdk/current/lib/keyos/api/usb" }   # ⚠️ NOT shipped by 1.0.0
```

Keep the split; just repoint SDK paths to `.foundation-sdk`. **But if the device side depends on a KeyOS API the packaged SDK doesn't ship, that dep cannot resolve** — the clearest case is **`api/usb`** (the `os/usbdev` vendor-interface transport): `foundation build` targets `armv7a-unknown-xous-elf`, pulls the `cfg(target_os = "xous")` set, and dies at the missing `usb` crate. The 1.0.0 SDK exposes 12 API crates (app-manager, backup, camera, crypto, fs, gui-server, haptics, nfc, quantum-link, rgb-led, security, settings) and **no callable `bt` or `usb` API**. An internal crate named `bt` carries only `BluetoothError` so the temporary QuantumLink v1 API can compile; it has no `BluetoothApi` or messages. Options for the maintainer: (a) wait for the SDK to grow the surface, or (b) ship a **partial port** — feature-gate or stub the transport so the UI, on-device key derivation, and signing still build and run (a stubbed transport that injects one canned request can drive the full approval UI and real on-device crypto; only the USB link is absent). See §14 for the reusable pattern.

**Vendored KeyOS crates can be dropped.** 0.4.0 apps often vendored crates the 0.4.0 SDK didn't ship — most commonly `vendor/security-api` (the `security` API crate) and `vendor/getrandom` (KeyOS's TRNG fork of getrandom). 1.0.0 ships both (`api/security`, `imports/getrandom`), so delete the `vendor/` copies and point at the SDK instead:

```toml
# was: security = { path = "vendor/security-api" }
security = { path = ".foundation-sdk/current/lib/keyos/api/security" }

# was: [patch.crates-io] getrandom = { path = "vendor/getrandom" }
[patch.crates-io]
getrandom = { path = ".foundation-sdk/current/lib/keyos/imports/getrandom" }   # already in the scaffold
```

The SDK `security` crate is nearly a drop-in for the vendored one 0.4.0 apps used (`security::use_api!()`, `Security::default().seed()` returning `Result<Option<Seed>, AccessDenied>` with `Seed::to_vec()`) — **with one call-site difference: `app_seed()`**. The vendored `security-api` returned `Result<[u8; 32], AccessDenied>` (a raw array), but the SDK's returns an `AppSeed` newtype (`Result<AppSeed, AccessDenied>`) whose bytes come from `.as_bytes() -> &[u8; 32]`. So any code that passed `&app_seed` (a `&[u8; 32]` under the vendored crate) must become `app_seed.as_bytes()`:

```rust
// was (vendored app_seed() -> [u8; 32]):
wallet_core::generate(variant, Some((&app_seed, index)))
// now (SDK app_seed() -> AppSeed):
wallet_core::generate(variant, Some((app_seed.as_bytes(), index)))
```

Everything else — `seed()`, `use_api!()`, the permission model — is unchanged.

### 3.2 Generated / ignored artifacts

- `ui/ui` — symlink to the SDK's Slint widget library, created by `foundation build`/`sim` (it targets the *versioned* SDK directory; after an SDK update run `foundation clean` then rebuild to refresh it).
- `target/foundation/**` — new private staging tree: converted image assets, per-app generated theme `.slint` files, `sim-resources`. Never edit.
- `manifest.toml` (app root) — generated from `app-config.toml` + `permission_templates.toml` on build, gitignored. 1.0.0 adds `publisher`, `description`, `version`, `qrMatchRules`, `fileHashes` (sha256 of each bundle file, covered by the signature) to the schema, which is now versioned (`manifestVersion = "0"`).
- `AGENTS.md` (new) — agent guidance generated into every app.

### 3.3 build.rs

0.4.0:

```rust
use slint_keyos_platform_build::{compile_options, CompileOptions};

fn main() {
    let out_dir = std::env::var("OUT_DIR").expect("OUT_DIR is set by Cargo");
    foundation_themes::build::compile_app_theme_json(
        "theme/theme.json",
        std::path::Path::new(&out_dir).join("app_theme.rs"),
        "app_theme",
    ).expect("compile app theme JSON");

    compile_options(CompileOptions { module_path: "ui/app.slint", /* … */ });
}
```

1.0.0 — the theme step is gone; the script re-exports the theme cache location instead:

```rust
use slint_keyos_platform_build::{compile_options, CompileOptions};

fn main() {
    let themes_rust_dir = std::env::var("FOUNDATION_THEMES_RUST_DIR").unwrap_or_else(|_| {
        let home = std::env::var("HOME").unwrap_or_else(|_| ".".to_string());
        format!("{home}/.foundation/themes/rust")
    });
    println!("cargo:rustc-env=FOUNDATION_THEMES_RUST_DIR={themes_rust_dir}");
    println!("cargo:rerun-if-env-changed=FOUNDATION_THEMES_RUST_DIR");

    compile_options(CompileOptions { module_path: "ui/app.slint", /* … */ });
}
```

`CompileOptions` itself is unchanged (`module_path`, `include_slint`, `include_router`, `include_translations`, `include_time_localization`) — carry over your settings.

If you called the translation codegen directly (rare): `slint_keyos_platform_build::localizer::build_translations(dir, out, gen, bool)` moved to the standalone `localizer-codegen` crate as `localizer_codegen::build_translations(dir, out, gen, &TranslationOptions { slint, include_time_localization })`. There is also a new `compile_service_translations()` for Slint-free headless services. Apps that only use `compile_options` are unaffected.

## 4. Slint UI changes

### 4.1 `@ui/theme.slint` imports (compile-breaking in every app)

```slint
// 0.4.0
import { Theme, UISize, ButtonStyleProps, ButtonSizeProps, ButtonVariant, ButtonState, ButtonSize } from "@ui/theme.slint";

// 1.0.0
import { Theme, UISize, Images, ButtonVariant, ButtonState, ControlSize } from "@ui/theme.slint";
```

- `ButtonSize` → **`ControlSize`** (same `sm/md/lg`). Every `size: ButtonSize.md` on a `Button` becomes `size: ControlSize.md`. Only `Button` changed; `ChipSize`, `SpinnerSize`, `IconButtonSize` are untouched.
- `ButtonStyleProps` → renamed **`ButtonVariantProps`** and moved to `@ui/button_theme.slint` (same fields). `ButtonSizeProps` moved there unchanged. Import from `@ui/button_theme.slint` if you used them.
- `Theme.get-button-style(variant, state)` → `ButtonTheme.style(v, st)`; `Theme.get-button-size(size)` → `ButtonTheme.size(s)` (in `@ui/button_theme.slint`).
- The `Theme.unset-color/-length/-int/-float/-string` sentinels and the `Theme.color()/length()/int()/float()/string()` resolver functions are **gone**. Component override properties now default to live theme values — just set the ones you override.
- Remember to re-export what `main.rs` needs: the template now does `export { Callbacks, Theme, Images, ButtonVariant, ButtonState, ControlSize }`. **Exporting `Images` is required** — `app_ui2!` binds it from Rust.

The `Theme` global lost the 25 per-variant button props (`primary-normal` … `danger-disabled`) and `size-sm/md/lg`, and gained a much richer token surface: named text roles (`font-size-title/body/subtitle/label/helper`), `palette-card`, 19 `color-*` tokens (`color-primary`, `color-danger-light`, `color-success`, …), plus `font-*`, `font-weight-*`, `control-size-*`, `icon-size-*`, `radius-*`, `control-radius-*`, `control-padding-inline-*`, `spacing-xs…xl`. The 11 `palette-*` names from 0.4.0 all survive.

All 29 widgets keep their names and callbacks; they additionally expose many new override `in` properties (e.g. `Card.title-color`, `Input.…`), and `MediaImage` (the component `@ui/image_view.slint` exports) gains `fit`. One behavioral note: `ButtonTheme` defines no `loading` styles anymore — `ButtonState.loading` falls through to the `normal` style (0.4.0 had dedicated loading styles).

### 4.2 App assets: the new `Images` global

New pipeline (replaces ad-hoc image handling):

- Put images in **`resources/images/`** (`.svg .png .jpg .jpeg .webp .bmp`). `foundation build`/`sim` converts them via `foundation-asset-tool` to `.raw` staged under `target/foundation`.
- Load them in Slint with `Images.image("name")` (path without extension, e.g. `resources/images/logo.svg` → `Images.image("logo")`). Lookup searches the app bundle first (`fs::Location::AppResources`), then the shared SDK assets.
- ⚠️ **`Images.image()` does not pick up `name-dark.*` siblings.** The loader supports them, but `app_ui2!` binds `Images.image` with `is_dark = false` hard-coded (`slint-keyos-platform/runtime/src/lib.rs:159-161`), so the light asset serves both schemes. Only the legacy in-tree `Images.common`/`nine-slice` bindings read `CurrentTheme.is-dark`. Shipping a `-dark` image is therefore wasted bytes; switch assets yourself off the theme (`Theme.is-dark ? Images.image("logo-dark") : Images.image("logo")`). This is separate from the **launcher icon**'s dark variant (gotcha 11), which the build and launcher handle.
- `Images.icon("path", size)` serves the built-in icon set (39 shared SDK icons, `icon_set_ui2.bin`).
- Put fonts in **`resources/fonts/`** (`.ttf .otf .ttc`); they are registered before Slint starts and referenced by real family name (default family is Montserrat). Legacy root `images/` and `fonts/` dirs are still staged for compatibility, but move them.

### 4.3 Slint toolkit 1.12 → 1.17

No breaking Slint-language changes surfaced in the bundled compiler diff, and existing template UIs compile unchanged aside from the `@ui` import fixes above. Additions you can now use: `DragArea`/`DropArea`, `FlexboxLayout`, `Tooltip`/`TooltipArea`, `RadioGroup` (std-widgets), `Window.minimized/maximized/safe-area-insets/virtual-keyboard-*`, `FocusScope.focus-on-click/focus-on-tab-navigation` and `capture_key_*`, per-corner border radii, `box-shadow` `spread`/`inset`. (`Rotate` was replaced by `Transform` internally, but `rotation-*` properties remain as aliases.)

Also new: an internal `@theme` import namespace resolves to the per-app generated theme dir (`FOUNDATION_THEMES_SLINT_DIR`, set by the CLI) with fallback to `@ui` defaults; `@ui` itself can be overridden via `FOUNDATION_UI_LIBRARY_PATH`.

### 4.4 ui2 component-API drift ⚠️

1.0.0 reworked every ui2 component around the schema-driven theme pipeline, and some component **APIs** changed, not just theming. The clearest case: **`Dialog` lost its content props** (`title`, `message`, `primary-action`, `secondary-action`, and the `primary-clicked`/`secondary-clicked` callbacks) in favor of composition — it now exposes `open`/`variant`/`dismissable` plus styling knobs, with content and action buttons supplied as children. When a component stops compiling on 1.0.0, read its `@ui` source (via the `ui/ui` symlink) — the property surface is the authority.

A **behavior** note verified on hardware: **`Button` has schema-driven minimum heights** (`min-height` sm 52 px / md 60 px / lg 68 px, generated from `button.schema.json`). The 0.4.0 idiom `HorizontalLayout { height: 48px; Button { … } }` still renders — the label reserves one text line and the padding gives way first — but at very small forced heights (≤ 40 px) the label can still disappear. Prefer letting buttons take their `preferred-height`. The legacy per-instance styling overrides (`background`, `foreground`, `border-*`, `font-*`, `button-opacity`, `touch-expansion`) all still exist and behave.

## 5. Entry point: `app_ui!` → `app_ui2!`

`app_ui!` **no longer exists** in 1.0.0. In `src/main.rs`:

```rust
// 0.4.0
use slint_keyos_platform::app_ui;
app_ui!("{{friendly_app_name}}");            // optional: , kind = App, height = …
fn app_main(_cx: AppContext, ui: AppWindow) { … }

// 1.0.0
use slint_keyos_platform::app_ui2;
app_ui2!("{{friendly_app_name}}");           // optional: , height = …
fn app_main(cx: AppContext, ui: AppWindow) { … }
```

- The `kind = …` parameter is gone, and the `gui_server_api::AppKind` enum is deleted. SDK apps always register as ordinary app windows. (System roles — keyboard, control center, launcher, lock screen, … — are claimed via the new `GuiApi::register_with_role::<M: msg::RoleClaim>` / `register_keyboard` / `register_control_center`, using Foundation-only `Claim*Role` messages.)
- **If the source app uses `app_minimal!`** (an entry macro from interim development bundles that exists in *neither* packaged SDK), the same rename applies (`use slint_keyos_platform::app_minimal;` → `app_ui2;`, `app_minimal!("…")` → `app_ui2!("…")`), and any hand-rolled image init (`_internal_init_images_with_theme!(Images, Theme, ui, cx)`) is dropped: `app_ui2!` binds `Images` for you. **It does not apply your theme**; that stays your job, through the generated `src/theme.rs` calling `apply_theme!` from `app_main` (§6); drop the hand-rolled init without wiring that up and the app renders on default light. These apps usually also carry the *old* 0.4.0 theme pipeline (build.rs `compile_app_theme_json` + a hand-written `theme.rs`), which the port replaces wholesale per §6.
- Everything else about the expansion is shape-compatible: your root component must still be `export component AppWindow inherits Window`, `app_main(cx: AppContext, ui: AppWindow)` is unchanged, `AppContext` still provides `gui`, `fs`, `router`, `config`, `set_input_handler`.
- New in the expansion: `app_ui2!` binds the `Images` global (hence the export requirement in §4.1).

## 6. Theming: the biggest rework

### 6.1 Old vs new flow

| | 0.4.0 | 1.0.0 |
|---|---|---|
| Theme source | `theme/theme.json` | `resources/theme.json`, declared in `app-config.toml` as `theme = "resources/theme.json"` |
| Compilation | `build.rs` → `OUT_DIR/app_theme.rs` | `foundation` CLI → `~/.foundation/themes/rust/<id>.rs` (`foundation themes build`, invoked automatically by `build`/`sim`) |
| Inclusion | `include!(concat!(env!("OUT_DIR"), "/app_theme.rs"))` | `foundation_themes::include_theme!(app_theme);` |
| Application | ~200 hand-written lines (`apply_theme`, `button_style`, `button_size`, `token_color`, per-variant `Theme` setters) | `foundation_themes::apply_theme!(ui, app_theme::theme(), scheme);` |
| Editing | hand-edit JSON | `foundation theme` (visual editor) or hand-edit JSON |

The new `src/theme.rs` is ~40 lines; the system-theme subscription loop (`subscribe_scalar::<SettingsPermissions, _>(SubscribeSystemTheme)` → `ColorScheme::Dark/Light`) is unchanged. App-specific tweaks go at the bottom of `apply_system_theme()`, after the inherited theme is applied:

```rust
foundation_themes::apply_theme!(ui, app_theme::theme(), scheme);
// App-specific overrides:
ui.global::<crate::Theme>().set_font_size_title(28.0);
```

**Do not port your 0.4.0 `theme.rs`** — it cannot compile: the `Theme` Slint global no longer has `set_primary_normal`, `set_size_sm`, etc. (Button styling now flows through the generated `ButtonTheme` global.) The old Rust types (`ExportTheme`, `get_component_style`, `ComponentState`, `TokenValue`, `ThemeColor`, `compile_app_theme_json`) are still re-exported for legacy code, but the templates no longer use them.

### 6.2 Theme JSON

- Your app theme file is still tiny: `{ "id": "app_theme", "name": "…", "parent": "<base>" }`. Move it from `theme/theme.json` to `resources/theme.json`. A 0.4.0 theme that carried **token overrides** ports 1:1 — keep the scaffold's `parent` and paste your `tokens` section into it (verified on hardware: light-mode `surface`/`primary` overrides render identically on 1.0.0).
- **Base themes shrank — and the survivor was renamed**: 0.4.0 shipped `default_theme`, `my_custom_theme`, `verdant_theme`, `sunset_serif`, `signal_mono`; 1.0.0 ships exactly one base, **`base_theme`** (`default_theme` lives on as a legacy alias — the CLI normalizes it, and a leftover `default_theme.json` seed coexists harmlessly). New scaffolds write `"parent": "base_theme"`; keep it. If your 0.4.0 app inherits one of the removed bases, copy that base's JSON into `~/.foundation/themes/json/` (or `foundation themes new <name>` and re-apply its values), or your theme won't resolve. A theme that carries its **own full token set and no `parent`** doesn't touch base-theme resolution at all.
- Token schema is unchanged (`tokens.{colors.{light,dark}, spacing, controlSize, iconSize, controlRadius, controlPaddingInline, typography, radius}`); 1.0.0 makes more of the `Theme` global themable, and these are the keys as you write them in JSON: `typography.font-size-{xs,caption,helper}`, `fontWeight.semibold`, `borderWidth.{none,sm,focus}`, `choiceControlSize.{sm,md,lg}`, `switchSize.{sm,md,lg}`, `colors.{light,dark}.transparent`. Note that font sizes live under `typography` while the rest are top-level `tokens` sections, and that `typography.font-size-xl` and `-2xl` are accepted by the compiler but set a token no `Theme` property reads, so they do nothing. An unrecognised token section is dropped without a warning, so a misspelt key fails silently: check a change actually landed rather than assuming it did.
- New optional **`components.<key>` section** for per-component overrides (`variantProps`: variant → state → prop, `sizeProps`: size → prop, values are literals or token refs like `"color.primary"`). These are inlined into per-app generated `<key>_theme.slint` files; the contract (variants/states/sizes per component) is schema-driven — `ui2/theme-editor/defaults/components/*.schema.json`, one per component with full coverage of the component set. The visual editor (`foundation theme`) is built around these schemas and has undo/redo.
- **Custom brand themes** — instead of inlining tokens in the app theme, create a reusable named theme with `foundation themes new <brand> --from base_theme` (writes `~/.foundation/themes/json/<brand>.json` with empty `tokens` + `parent: base_theme`), fill in its `tokens.colors.{dark,light}` overrides, then point the app at it: `resources/theme.json` → `"parent": "<brand>"`. `foundation build` stages the whole parent chain (`app_theme` → `<brand>` → `base_theme`).
- Theme cache: `~/.foundation/themes/json/` (sources, seeded on first use) → `foundation themes build` → `~/.foundation/themes/rust/`. That path is **not** relocatable: `foundation themes` and the theme editor both derive it from `dirs::home_dir()`, so the `FOUNDATION_THEMES_DIR` override that `foundation_themes::themes_dir()` reads never reaches them. The compile-time lookup uses `FOUNDATION_THEMES_RUST_DIR` (set by `foundation build`/`sim`; the template build.rs defaults it to `~/.foundation/themes/rust`). ⚠️ The **app-local** theme (`app_theme`, from the app's `resources/theme.json` — which the template's `theme.rs` always includes) is staged into the app's **`target/foundation/themes/rust/`** by `foundation build`, NOT into `~/.foundation/themes/rust/` by `foundation themes build` — so plain `cargo check`/`cargo test` fails with `couldn't read ~/.foundation/themes/rust/app_theme.rs` until you run one `foundation build` and then invoke cargo as `FOUNDATION_THEMES_RUST_DIR=$PWD/target/foundation/themes/rust cargo test`.

## 7. app-config.toml, permissions, manifest

### 7.1 app-config.toml

Same keys as 0.4.0 (`app-name`, `friendly-app-name`, `launcher-app-name`, `description`, `icon`, `app-id`, `version`, `min-keyos-version`, `[publisher] name/contact-email/support-url`, `[permissions] template = ["gui-app"]`, optional `signing-identity`/`cosign2-config`) **plus one new required-by-template key**:

```toml
theme = "resources/theme.json"
```

### 7.2 permission_templates.toml — regenerate, don't copy

Syntax is unchanged, but the shipped content moved:

- `[gui-app]`'s `"os/fs"` list **adds `OpenFileMessage`, `CloseFile`, `ReadFile`**. This is mandatory: the runtime's `GuiAppFsPermissions` trait now requires those three messages (image loading reads from the app bundle), so an app carrying the stale 0.4.0 template fails to compile.
- `[fs-generic]` drops `FlushFs` from the template — but the **message still exists** (`os/fs` `FlushFs`, `id 20`, `autoAllow`), and the fs crate's `FileSystem::flush(location)` still requires `MessageAllowed<FlushFs>`. So an app that calls the *filesystem-level* `flush()` (as opposed to file-level `Flush`) now fails to compile — `error[E0277] … required by a bound in FileSystem::<P>::flush` — unless you grant `FlushFs` yourself. Add it to the app's direct `"os/fs"` grants (`"os/fs" = [… , "FlushFs"]`). This is a template change, not a service change: nothing about `flush()` behavior moved, the default template just no longer carries the permission. **⚠️ But note (§7.3): `FlushFs` is _ungrouped_, so it is Foundation-signed-only — granting it fixes the compile error, but a third-party-signed app is still denied when it actually calls `flush()`. That denial comes back as an `fs::Error` rather than a panic (§7.3), so you can handle it; prefer file-level `Flush` (grouped, third-party-OK) on the `File` handle where you can.**
- The `[i2c]` (`os/i2c`) and `[gpio]` (`os/gpio`) templates are **removed** — those permissions are no longer offered to SDK apps.
- `[navigable]` is unchanged.

### 7.3 The new permission model

Every service manifest message now carries policy metadata (schema `manifestVersion = "0"`):

| Field | Values | Meaning |
|---|---|---|
| `permissionGroup` | `"<group>.<subgroup>"` (e.g. `peripherals.camera-use`) | Groups the message in the permission/consent UI |
| `approval` | `autoAllow` \| `grantOnFirstUse` \| `notUserGrantable` (default) | Whether/how the user grants it |
| `requiredSignature` | `thirdParty` \| `foundation` | Default derived: grouped → `thirdParty`, ungrouped → `foundation` |

Practical rule for third-party-signed apps: a message is grantable to you only if all three fields agree, the way the "resolve its real availability" bullet under *Practical consequences when porting* spells out. `approval` mostly decides *how* a grantable message is granted (`autoAllow` = silently, `grantOnFirstUse` = one consent prompt) rather than whether, with one exception in the other direction: `notUserGrantable`, which is the default when a message declares no `approval`, is never grantable whatever its group and signature resolved to. An ungrouped message is Foundation-only no matter its `approval`, unless it sets `requiredSignature = "thirdParty"` explicitly (`api/gui-app-emu-flux` does, for its Flux children); you can list a Foundation-only message in your manifest, but calling it is refused, and for most APIs that refusal is a panic rather than an error (see below).

**A message your app cannot hold does not fail gracefully: the call is refused, and wherever the API wrapper unwraps that refusal the app crashes, verified on hardware. And `approval = "autoAllow"` does NOT mean third-party-usable.** The single most important rule of the 1.0.0 permission model: **grantability is resolved from `permissionGroup`, `requiredSignature` and `approval` together, and `autoAllow` is not one of the fields that grants it.** The common case is that a `permissionGroup` makes a message third-party-grantable and its absence makes it Foundation-signed-only, **even if its `approval` is `autoAllow`**; but an explicit `requiredSignature` overrides the group either way, so grouped-and-Foundation-only is real (see the `os/settings` and `os/quantum-link` cases below). Reading `autoAllow` in a service manifest and assuming a third-party app can call it is the trap. Examples that bite real ports:

| Message | approval | permissionGroup | third-party? |
|---|---|---|---|
| `os/fs` `WriteFile`, `Flush` (file-level) | autoAllow | `file-system.write-and-mutate` | ✅ yes |
| `os/fs` `GetUserWriteAccess`, `GetAirlockWriteAccess` | grantOnFirstUse | `file-system.*-files` | ✅ yes (prompts once) |
| `os/fs` **`FlushFs`** (filesystem-level flush) | autoAllow | *(none)* | ❌ **Foundation-only** |
| `os/fs` **`MountAirlock`, `FormatAirlock`** | autoAllow | *(none)* | ❌ **Foundation-only** |
| `os/security` **`GetSeed`** | autoAllow | *(none)* | ❌ **Foundation-only** (the master seed itself is `autoAllow`) |
| `os/security` **`GetDeviceId`** | autoAllow | *(none)* | ❌ **Foundation-only** (classic `autoAllow`-but-ungrouped trap) |
| `os/security` `GetAppSeed` | grantOnFirstUse | `device-secrets.app-scoped-seed` | ✅ yes (prompts once) |
| `os/bt` `GetState`, `SubscribeBleState` | autoAllow | `device-connectivity.bluetooth-status` | ✅ yes |
| `os/bt` **`EnableBle`, `GetBtAddr`** | autoAllow | *(none)* | ❌ **Foundation-only** |
| `os/bt` **`Disconnect`** | *(unset → notUserGrantable)* | *(none)* | ❌ **Foundation-only** |
| `os/quantum-link` **`GetXidDocument`, `UnpairFromEnvoy`** | autoAllow | *(none)* | ❌ **Foundation-only** |

When a third-party app calls a Foundation-only message the call is refused, and wherever the API wrapper unwraps that refusal the SDK **panics instead of returning an error** and the app aborts (exit 255) to the crash-report screen. Two failure signatures seen on device:

- *Connection-level* (`os/security` `GetSeed`): the app can't even connect to the server. `xous_names: App AppId(…) tried to connect to os/security without permissions`, then `server/checked_conn.rs` `.unwrap()`s the refused connection → panic.
- *Message-level* (`os/fs` `MountAirlock`, `FormatAirlock`): the app is connected to `os/fs` (it has grouped fs permissions), but the specific ungrouped message is refused. `mount_airlock()` / `unmount_airlock()` / `format_airlock()` send it via `server/scalar.rs` `send_blocking_scalar`, which is literally `try_send_blocking_scalar(…).unwrap()` → panic `AccessDenied`, *no* `xous_names` warning, and no chance for the app's own error handling.

**Which of the two signatures you see is decided by the permissions; whether a message-level denial panics or comes back as an error is decided by the API wrapper.** No *holdable* grant on the server gets you the connection-level refusal: `effective_permissions` marks a server connectable only once some granted message resolves to available, so an app whose only `os/security` grant is `GetSeed` is refused the connection outright. A holdable grant plus a separate ungrouped message gets you the message-level one. From there, whether it panics depends on which send the fs crate used. `FileSystem::flush()` uses `try_send_blocking_scalar` (`api/fs/src/lib.rs:379-384`), so a refused `FlushFs` comes back as an `fs::Error` you can match on and handle. Keep your error handling on that path. It is the Airlock mount/format calls that give you no such option.

Under a Foundation-only denial the connection-level case always aborts the app, and the message-level case aborts it wherever the wrapper unwraps. This holds even when the app's publisher certificate has been added to Allowed Publishers: that allows a third-party app to *install and run*, but Foundation-only messages stay reserved for Foundation-signed apps. Practical consequences when porting:

- **Grep the service manifests for every message you grant and resolve its real availability**, which takes all three fields: a `permissionGroup` (or an explicit `requiredSignature = "thirdParty"`), no `requiredSignature = "foundation"` overriding that group, and an `approval` of `autoAllow` or `grantOnFirstUse`. Grouped-but-Foundation-only is a live combination (`os/settings` device-configuration reads, `os/quantum-link` wallet-sync), so a group alone is not the all-clear. Anything that fails the resolution is refused at the call, which aborts the app wherever the API wrapper unwraps it. Do this *before* sideloading, so you know whether the app can actually run.
- **`GetSeed`** (real master-seed entropy) must never appear in an SDK app's manifest — see gotcha 21: it is always an app-side mistake; derive from the grouped `GetAppSeed` (`grantOnFirstUse`) instead. Note the outputs are per-app and bound to the master seed plus the app-id, not to the device — a deliberate, documented behavior change if the original app derived from the master seed.
- **`MountAirlock`/`FormatAirlock`/`FlushFs`** block any app that exports to the USB-visible **Airlock** volume or calls filesystem-level `flush()`. `FlushFs` is the mild one: it is denied but `flush()` returns that denial as an error, so file-level `Flush` (grouped) replaces it and you keep your error path either way. Writing to **User/Internal** storage works (grouped `WriteFile` + `GetUserWriteAccess`). But mounting Airlock has no third-party equivalent, which is a problem for apps whose purpose is "write a file the user carries off over USB". If your app needs one of these, raise it with the KeyOS team (they can add a `permissionGroup` to make it third-party-grantable) rather than working around it.
- There is no way to make a Foundation-only message work from a third-party-signed app; don't burn time trying.

**The Airlock volume is also gated at runtime by USB, independently of signing.** While a host computer is connected over USB, the system hands the Airlock (mass-storage) volume to the host, so the device side cannot write to it — `mount_airlock()` / Airlock writes fail. **This bites you during development**, because the same USB cable you use for `foundation sideload` / `passport-drive` is what locks Airlock: an app that exports to Airlock will fail exactly while you're driving it over USB. Two consequences for a ported app:

- An app that writes to Airlock should tell the user to **unplug USB first**, and it can make that conditional: `os/settings` `GetAirlockMode`/`SubscribeAirlockMode` and `GetUsbEnabled`/`SubscribeUsbEnabled` sit in the `device-connectivity.usb-device-status` group (`autoAllow`, third-party-readable), so grant them and gate the export flow on the actual plugged state, exactly like the built-in File app does by reading `AirlockMode` from settings.
- Because `mount_airlock()` sends a `send_blocking_scalar` that **`.unwrap()`s the denial into a panic** (see above), the app can't catch the "Airlock busy / not permitted" failure and show a message — it just crashes. So while USB is connected you often *cannot tell apart* the two causes (Foundation-only signature vs. host-owns-the-volume); both surface as the same `AccessDenied` panic. Test Airlock export with USB unplugged (e.g. save to Internal over USB for iteration, and verify Airlock export separately on an unplugged device).

Two long-standing gotchas that remain true in 1.0.0:

- **Never grant simulator-only messages** (`cfg = "not(keyos)"` in the service manifests) in an app you'll build for hardware — the `server::Permissions` derive resolves every granted message name to a real type at compile time, so hardware builds break.
- Message *ids* are not stable across versions (e.g. `os/settings` id 77 was `GetUsbLogging` in 0.4.0 and is `GetBoardRevision` in 1.0.0) — never ship a stale generated `manifest.toml`; let `foundation build` regenerate it.

## 8. Rust service-API breaking changes

Ordered by likelihood of hitting a typical app. `bt`, `haptics` are unchanged; `rgb-led` is additive only (sim-only `subscribe_color_updates`).

### 8.1 `crypto` (largest rewrite)

AES:

```rust
// 0.4.0
let ctx = crypto.setup_aes(AesMode::Cbc { key: &key, iv: &iv })?;
ctx.execute(buf, offset, n_blocks, Direction::Encrypt)?;    // 3rd arg in 16-byte BLOCKS

// 1.0.0
let ctx = crypto.setup_aes(&key, AesMode::Cbc { iv })?;     // key is a separate arg; AesMode has no lifetime
ctx.execute(buf, offset, len_bytes, Direction::Encrypt)?;   // 3rd arg in BYTES
```

- ⚠️ **Silent semantic change**: `AesContext::execute`'s third parameter changed from *number of 16-byte blocks* to *number of bytes*. The arity is unchanged (`direction` is in both versions) and the parameter keeps its position and type (`usize`), so **old code compiles and corrupts**, and nothing but a careful read catches it. Multiply by 16 when porting.
- `AesMode` gains `Ctr { iv: [u8; 16] }` and `Gcm { iv: [u8; 12] }`; new `ctx.add_aad(&aad)` and `ctx.gcm_tag() -> [u8; 16]`.
- AES now also works in the simulator (messages lost `cfg = "keyos"`).

SHA — the DMA/`MemoryRange` API is gone; it's plain byte slices now:

```rust
// 0.4.0
let digest = crypto.sha256(mem_range, offset, len)?;
let ctx = crypto.sha_init(ShaAlgo::Sha256, total_len)?;
ctx.update(mem_range, offset, len)?;          // -> Result<usize, _>

// 1.0.0
let digest = crypto.sha256(&data)?;           // requires the renamed messages (see below)
let mut ctx = crypto.sha_init(ShaAlgo::Sha256);   // infallible, no total_len
ctx.update(&data)?;                            // &mut self, -> Result<(), _>
let digest = ctx.finalize()?;
```

- Manifest message renames (update `permission_templates.toml`): `ShaInit` → `ShaSetContext`, `ShaFinalize` → `ShaGetContext`, `ShaAbort` → `ShaDrop`. The `Sha*` messages are hardware-only now (`cfg = "keyos"`); hosted/simulator builds hash in software.
- `SHA_DMA_ALIGNMENT` removed. Errors: `TooManyShaContexts` removed; `UnalignedDataLength`, `InvalidMode`, `InvalidState` added.
- `disk_encrypt_unsafe` now returns `Result<(), _>`; completion arrives via new `subscribe_disk_encrypt_complete`.

### 8.2 `gui-server`

- `GuiApi::register(AppKind::App, name, height)` → `GuiApi::register(name, height)`; `AppKind` deleted (see §5).
- `GuiApiLight::try_connect()` / `try_connect_with_timeout(d)` (returned `Option`) → blocking `connect()`.
- `update_keyboard(kind, request_caps)` → `update_keyboard(msg: msg::UpdateKeyboard)`; the struct gains `accept_button_text`, `accept_button_enabled`, `delete_button_enabled`.
- Removed: `show_control_center()`, `hide_control_center()`, `set_wake_lock(bool)` (messages deleted; **no wake-lock replacement**). Partial successors: `set_control_center_color(Option<ControlCenterColor>)` (grouped `ui-and-input.control-center-appearance`, so third-party-grantable) and `update_kiosk_policy(msg::UpdateKioskPolicy)` (**ungrouped, Foundation-only**). Same split among the app-id-taking calls below: `ShowModal` is grouped (`ui-and-input.brokered-modal`), while `NavigateTo` and `RunApp` are ungrouped and Foundation-only, `RunApp` with no `approval` at all. New: `is_locked()`, `inject_power_button(bool)`.
- App-id plumbing is typed now: `ShowModal` / `NavigateTo` / `RunApp` take `AppId` instead of `[u8; APP_ID_SIZE]`; navigation constants are used directly (`QR_SCANNER_APP_ID`, not `.0`). `RunAppResponse::LaunchFailed` gained `{ reason: LaunchFailureReason }` (`SignatureRejected` / `NoCertificate` / `Internal`).
- QR scanner results restructured: `ScanQrResult::Qr(Vec<u8>)` → `Qr { data, matching_apps: Option<Vec<ScanQrMatchingApp>> }` (same for `Ur2`); `ScanQrOptions` gains `request_matching_apps`. New `navigation::async_open_qr_scanner`.
- `navigation::open_bitcoin_app` and the whole `navigation::bitcoin` module are removed. `BITCOIN_APP_ID` itself survives alongside the other navigation app-id constants, so reach the app through the generic `run_app`/`navigate_to` instead of looking for a replacement constant. Security-keys outcome notifications moved to `os/fido`'s `SubscribeOperationOutcomes`, **which an SDK app cannot reach**: no `fido` API crate ships in the bundle, and the message is ungrouped, so Foundation-only. The move matters to the built-in Security Keys app, not to a port; an app that consumed these notifications treats them as a missing surface (§14).
- `close_app(pid)` is now blocking and can fail (`CannotCloseEssentialApp`, `AppNotFound`, `AppAlreadyClosing`).
- Behavioral: `invoke_alert` presents as `SlideUpFixedPopup` (was fullscreen slide-up); simulator `DEVICE_WIDTH` 576 → 592 (pixel-exact tests/screenshots shift).

### 8.3 `fs`

- `Location` enum gained **`AppResources`** (read-only view of your installed bundle — where `resources/**` ends up). Exhaustive `match`es on `Location` stop compiling; writes there return `AccessDenied`.
- `map_file` bound changed: `MessageAllowed<MapFileMessage>` → `MapFilePermissions` (on hosted builds this also wants `OpenFileMessage`+`CloseFile`+`ReadFile` — already in the new `gui-app` template).
- `disk_encryption_keys_ready()` and its message are gone → `os/security`'s `SubscribeDiskEncryptionKeysReady`. **Foundation-only** (ungrouped, no `approval`), and the wrapper subscribes infallibly, so a sideloaded app that grants it aborts on the denial; a third-party port has no readiness signal to wait on and should just not wait.
- New: `register_app_resources`, `remove_app_data`, `FileHandle/DirHandle::{new, id, location}`.

### 8.4 `settings`

- Removed (methods + messages + types): USB-logging and MCP-control get/set/subscribe (`global::UsbLogging`, `global::McpControl`).
- New: `get_board_revision() -> global::BoardRevision { D1, D6 }`.
- Everything else (locale, theme, brightness, time…) is path-compatible; third-party-readable settings live under the `settings.ui-essentials` group.

### 8.5 `app-manager`

- `AppEvent` restructured — every `match` breaks: `app_id` fields are `AppId` now (was `[u32; 4]`); `LaunchError(e)` → `LaunchError { app_id, error }`; new variant `AppSetChanged { installed, removed }`.
- `GetAppName::ByAppId` id field: `[u32; 4]` → `AppId`.
- `decode_app_id_str` now **requires the `0x` prefix** (0.4.0 accepted bare hex).
- Grew from 4 to 14 messages. Of the additions, a third-party app can hold only the `app-management.app-metadata` trio: `get_app_name`, `get_app_icon`, `get_qr_match_rules`. The admin surface (`list_apps`, certificate import/remove, `set_app_permission_grant`, `remove_installed_app`, `refresh_installed_apps`, `get_permission_request_info`) is ungrouped, so Foundation-only, and several of those wrappers send infallibly, so calling one aborts a sideloaded app.

### 8.6 `quantum-link`

- `clear_paired_device()` and `ClearPairedDevice` are gone → send the new `UnpairFromEnvoy` message (response `Result<(), SendMessageError>`); no convenience wrapper exists.
- `RestoreShard` gained a `timestamp: u32` field (struct literals break).
- New `SendPrimeFiatPreference { currency_code }`; several Envoy-sync messages are Foundation-signature-gated.

### 8.7 `server` crate (affects any custom message/IPC code)

- `server::xous_ipc` re-export removed → `xous_ipc::Buffer` becomes `server::Buffer` (`Buffer::send(conn, id)`, `Buffer::from_bytes`); `rkyv_with::WithUnixTimestamp` → root `server::WithUnixTimestamp` (new sibling `WithAppId`). Rkyv itself only moved 0.8.15 → 0.8.17 (already rancor-based; `XousDeserializer`/`XousValidator`/`XousSerializer` aliases now live at the server root — `quantum-link`'s worker imports changed accordingly).
- `CheckedConn::{send_blocking_archive_buf, try_send_blocking_archive_buf, send_blocking_archive_async}` and their free-fn variants are removed; new `CheckedConn::try_lend_mut`. All the mainstream `send_*`/`subscribe_*` methods, `CheckedPermissions`, `MessageAllowed`, and the three derives are unchanged.
- `slint_keyos_platform::raw_image::load_icon` gained an `icon_set_file: &str` parameter (pass `slint_keyos_platform::UI2_ICON_SET`).

**Tooling**

- `foundation theme` / `foundation themes build|list|new` + visual theme editor and compiler binaries.
- `foundation clean` — removes `target/`, generated `manifest.toml`, `ui/ui`; run it after every SDK update.

The container carries **no signature of its own**: the cosign2-signed `manifest.json` and its `fileHashes` cover every other file, so trust is unchanged from a sideloaded bundle. The archive holds the manifest and exactly the files its `fileHashes` covers: the packer (the `app-archive` crate's `pack_bundle`) is handed that list by the build rather than walking the directory, so what ships is what the signature covers. Archives are reproducible: fixed mtimes/uid/gid and a sorted entry order, so the same bundle packs to identical bytes anywhere.

  The one cap `pack` enforces is the 64 MiB an install accepts, counted as the device reads it, tar framing included. Everything else about a bundle the device would refuse surfaces there as an install error. `--out` must not point inside the bundle being packed and must not be a symlink: creating the archive truncates whatever sits at that path, before the bundle is read.

## 10. Environment & workflow changes

- **GUI tools now require the dev shell.** The 1.0.0 `foundation-slint-viewer` (and friends) link against fontconfig/GL/wayland via the Nix `LD_LIBRARY_PATH` and fail outside it (`libfontconfig.so.1` not found) — the 0.4.0 binaries ran standalone. Run them through `foundation develop` (or `nix develop`).
- `foundation preview` resolves `@ui` against `<project>/target/foundation/ui/ui` first (per-app generated themes), falling back to the SDK — so preview *after* a first `foundation build`/`sim` to see your theme.
- The 0.4.0 CLI displayed localized command help; 1.0.0 prints English. Canonical command names are identical, plus the three new commands.
- `foundation sim` stages app resources under `target/foundation/sim-resources` and passes `FOUNDATION_APP_RESOURCES_DIR` to the hosted runtime.
- After **any** SDK update: `foundation clean && foundation build` in each app (refreshes the `ui/ui` symlink and regenerated manifest/themes), re-run `foundation doctor` — and **restart every shell or editor/agent session that was launched from inside a `foundation develop`**, or they keep the old bundle's `FOUNDATION_SDK_ROOT` and silently build against the old SDK (gotcha 13).
- Templates now ship a **`.mcp.json`** registering the `passport-drive` MCP server (screenshots, taps/swipes, logs on a real device; the device must have Developer Mode enabled) and an AGENTS.md section describing it. If an app predates these template files, copy both out of the SDK's template tree: `<sdk-root>/lib/templates/default-app/files/` in a packaged bundle, `<sdk-root>/crates/cli/templates/default-app/files/` in a source checkout.

## 12. Gotchas (ranked)

1. **AES `execute` unit change** (blocks → bytes): compiles clean, corrupts data. Audit every call.
2. **Stale generated `manifest.toml` / message ids**: ids were renumbered (`GetBoardRevision` now occupies old `GetUsbLogging`'s id 77; gui-server ids shuffled). Always regenerate via `foundation build`; `manifest.toml` stays gitignored.
3. **Old `permission_templates.toml`** without `OpenFileMessage`/`CloseFile`/`ReadFile` under `[gui-app]` → `GuiAppFsPermissions` trait bound fails; confusing compile error.
4. **Missing `Images` export** in `app.slint` → `app_ui2!` fails to bind the global.
5. **Base theme not found**: 1.0.0 seeds only `base_theme` (plus a legacy `default_theme` alias); the other 0.4.0 bases must be ported manually.
6. **`match` exhaustiveness**: `fs::Location::AppResources`, `AppEvent::AppSetChanged`, restructured `ScanQrResult` variants.
7. **Sim-only messages** (`cfg = "not(keyos)"`) in a manifest break hardware builds (unchanged rule, bigger surface now).
8. **GUI tools outside the Nix shell** fail on `libfontconfig.so.1` — use `foundation develop`.
9. **`decode_app_id_str`** now requires the `0x` prefix.
10. **Pixel-exact UI tests**: simulator width 576 → 592; alerts render as fixed popups; button `loading` state now styles as `normal`.
11. **App icon: exactly 110×110 px, transparent-background glyph only.** This bites *every* port because 0.4.0 icons are designed as square app tiles (with their own background) while the 1.0.0 launcher supplies the tile — and **`foundation build` only validates the icon's SIZE, never its transparency**, so a background slab passes the build and only shows up as a square over the round tile when you look at the launcher. Do it once, deterministically, at the icon step:

    **The two rules.** (a) *Size*: the root `<svg>` must be `width="110" height="110"` (keep the original `viewBox`); otherwise the build hard-errors (`Error: Icon must be 110x110px, but … is 256x256px`). PNG icons work too (same exact-size rule). (b) *Transparency*: the launcher renders your icon 1:1 into a 110×110 slot centered on its **own** 144 px badge plate (silver ring + copper accent + dark disc), so the asset must be a **glyph on a fully transparent background** — delete any full-canvas `<rect>`/`<circle>` fill. A background renders as a visible slab/halo. Size the glyph ~55–60 % of the canvas in a bright accent color (it sits on a near-black disc in both themes).

    **The port transform** (apply right after copying `resources/icon.svg`): set the root `width`/`height` to `110`, and **delete the first full-canvas background element** (the full-size `<rect>` or equivalent). Keep only the glyph paths.

    **Verify BEFORE building** (never trust the build or your eyes). Check the exact size, then render the icon over magenta and sample **8 points — the 4 corners AND the 4 mid-edges**; every one must show magenta through:
    ```sh
    magick identify -format '%wx%h\n' resources/icon.svg     # must print 110x110
    magick -background none -density 200 resources/icon.svg -resize 110x110 \
           -background '#ff00ff' -alpha remove -alpha off /tmp/i.png
    magick /tmp/i.png -format '%[pixel:p{2,2}] %[pixel:p{107,2}] %[pixel:p{2,107}] %[pixel:p{107,107}] %[pixel:p{54,2}] %[pixel:p{54,107}] %[pixel:p{2,54}] %[pixel:p{107,54}]' info:
    ```
    All 8 samples must read (near-)pure magenta — `srgb(255,0,255)`; a few percent of blend where a glyph stroke antialiases into a sample point is fine, any other color is a background. The `-background none` at read plus `-background '#ff00ff' -alpha remove` flatten is deliberate: it behaves identically for SVG *and* PNG sources (a plain `-background` before a PNG input does nothing, leaving transparent pixels unflattened and the check meaningless). Run the same check on the `-dark` sibling if you ship one. The mid-edge samples are what catch the **rounded-rectangle-background trap**: a bg `<rect rx="22">` has *transparent corners* (the `rx` cuts them) but *opaque mid-edges*, so a corners-only check passes a slab. If the source icon is a branded square tile (a gradient or dark rounded-rect behind the logo), the fix is always the same — **extract the logo/glyph paths, delete the background `<rect>`/`<circle>` entirely, and re-center the `viewBox` on the glyph** (recolor any dark logo body so it reads on the near-black disc). A glyph-only `icon.bin` is ~9–10 KB; a slab is ~48 KB — the byte size is an instant tell.

    **Dark-theme variant (optional).** Ship a `<stem>-dark.*` sibling of the configured icon (e.g. `resources/icon-dark.svg` next to `resources/icon.svg`, in any format the icon itself may use) and `foundation build` stages it as a second file, `icon-dark.bin`, beside `icon.bin`; the launcher and Settings pick the variant matching the current theme and re-render on live theme changes. Both files keep the same single-image format, and both are covered by the signed manifest's `fileHashes`. The dark sibling is validated to the same exact-110×110 rule (run the 8-point check on it too). Without a sibling only `icon.bin` is staged, and the light icon serves both themes.

    **Launcher cache caveat**: the launcher composites the tile bitmap once per app-id and keeps it in memory — re-sideloading a fixed `icon.bin` (even after uninstall/reinstall) does **not** refresh the tile; only a **device reboot** does. So after fixing an icon, the launcher looks unchanged until reboot even though `icon.bin` on disk is correct (its byte size will have dropped — a quick confirmation). To preview the fixed tile without rebooting, composite it offline: `magick -size 144x144 xc:none -fill '#231f20' -draw 'circle 72,72 72,12' disc.png; magick disc.png <(magick -background none -density 300 resources/icon.svg -resize 110x110 png:-) -gravity center -composite tile.png`. Apps that ship no icon get a fallback `grid-view` glyph.
12. **`simd-adler32` breaks device builds — pin `=0.3.7`.** Adding a crates.io dependency that pulls `simd-adler32` transitively (the `image` crate does, via `png` → `fdeflate`; so do many compression stacks) fails the `armv7a-unknown-xous-elf` build with a wall of `error[E0658]: use of unstable library feature 'stdarch_arm_neon_intrinsics'` — releases ≥ 0.3.9 use unstable NEON intrinsics on ARM. Add a direct `simd-adler32 = "=0.3.7"` entry (plus `cargo update -p simd-adler32 --precise 0.3.7`) to force the last good release; host/simulator builds are unaffected either way.
13. **A stale `FOUNDATION_SDK_ROOT` silently pins everything to an old bundle.** Any shell — or editor/agent session — started from inside a `foundation develop` inherits that bundle's `FOUNDATION_SDK_ROOT` and PATH, and SDK-root discovery trusts the env var first. After an SDK update, every foundation command run from such a session — *including a new `foundation develop`* — still uses the old bundle's binaries, templates, `@ui` widgets, and theme staging. The symptoms look like impossible bugs (stale templates, old component APIs, legacy theme seeds). When anything looks time-warped, `echo $FOUNDATION_SDK_ROOT`; after every SDK update, **restart such sessions**. Exporting `FOUNDATION_SDK_ROOT=$HOME/.foundation/sdk/current` is not enough on its own: PATH still resolves `foundation` and every `foundation-*` helper to the old bundle's `bin`, so you fix discovery and keep running the stale binaries, which is the harder version of the same bug to spot.
14. **`app_ui2!` does NOT wire translations — an app with `include_translations: true` renders all localized text blank until you wire i18n yourself** (the legacy in-tree `app!` did this automatically; verified on hardware). The build still generates `$OUT_DIR/tr.rs` (a `mod tr` with `TrId`, `lookup`/`lookup_id`, and the `init_tr!` macro), and the Slint side gets a generated `gen/tr.slint` with `TR2`/`TrId` — but `TR2`'s lookups are Rust-backed callbacks that nothing binds, so every string comes back empty. To fix, in `src/main.rs`: `include!(concat!(env!("OUT_DIR"), "/tr.rs"));` at the crate root; add `export * from "gen/exports.slint";` to `app.slint` (the generated module exports `TrId` and `TR2`, and `init_tr!` binds `crate::TR2`, so without it the macro fails to compile on a missing `crate::TR2` rather than producing blank strings); export a `TR` global from `app.slint` too (the legacy runtime i18n global: `pure callback lookup(string)->string; format(string,[string])->string; int/float`; a compat one is fine, and it is not in `gen/exports.slint`); call `init_tr!(ui)` in `app_main`; and add `phf = { version = "0.11", features = ["macros"] }` to `[dependencies]` (the generated tables use it). `init_tr!` binds every `TR2` callback, and `lookup` and `format` on `TR`.

    **It does not bind `TR.int` or `TR.float`.** If the legacy UI calls them, declare *and* bind those yourself, or replace the call sites. A declared-but-unbound callback returns the default silently, so this surfaces as a number-formatting bug rather than as missing wiring.

    Binding them is not a straight swap: the legacy callbacks are `int(int) -> string` and `float(float, int) -> string`, neither of which carries a locale, while `slint_keyos_platform::i18n::format_int(value, locale_str)` and `format_float(value, decimals, locale_str)` both require one. The closure has to supply it, and `tr::get_locale()` from the generated `tr.rs` is the natural source. **It must be a name `num-format` recognises**: `format_int` does `NumFormatLocale::from_name(locale_str).unwrap()` (`i18n/src/lib.rs:118-121`), so an unknown locale aborts the app rather than falling back, unlike its neighbour `format_file_size` (`:167`), which defaults to `en`. `format_float` calls `format_int` for the integer part, so it panics the same way.
15. **A C dependency (e.g. `secp256k1-sys`, pulled by bitcoin stacks) fails to cross-compile with `gcc: unrecognized -mfpu=vfpv3-d16`.** `cc-rs` defaults to the host `gcc` for the device target's build scripts, which rejects the ARM flags it emits. Add an app `.cargo/config.toml` pointing the target's C compiler at the cross toolchain (this matches the KeyOS workspace's own config):
    ```toml
    [env]
    CC_armv7a_unknown_xous_elf = "arm-none-eabi-gcc"
    ```
    `arm-none-eabi-gcc` is on `PATH` inside `foundation develop`. Pure-Rust dependency stacks avoid this entirely.
16. **Crypto-heavy apps HANG the device on unoptimized debug builds — add per-dependency `opt-level` to the dev profile.** `foundation build` uses the **dev (debug) profile**, and heavy crypto (curve25519-dalek scalar math, CLSAG/bulletproofs, RSA, k256) runs orders of magnitude slower unoptimized. Symptom (verified on hardware): the app logs its startup line, then the device goes **fully unresponsive** — the USB debug channel wedges (`bulk OUT write` fails), no panic in the log, requiring a physical power-button force-reboot. In one observed case the app's wallet init was spinning in unoptimized ed25519 math. Fix: optimize dependencies in the dev profile. Simplest and most robust is to optimize *all* deps while keeping the app crate debuggable:
    ```toml
    [profile.dev.package."*"]
    opt-level = 3
    ```
    (Listing specific crates — `[profile.dev.package.k256] opt-level = 3`, etc. — also works.) In-tree apps got this from the KeyOS workspace's profiles; a standalone port must set it. Debug an app that "hangs on launch" by reading the on-device log (`/run/media/<user>/ENCRYPTED/user/.log/log.*.log`): if the last app line is the startup banner with no panic after, it's a compute hang → this. **Addendum: if the hot code lives in the APP crate, optimize it too.** Deps-at-3 is not enough when the app crate itself does per-pixel rendering or protocol-pump work on the UI thread — at app opt-level 0 a single tap can wedge the device the same way. Add `[profile.dev] opt-level = 2` (or 1) alongside the deps rule; you lose a little debuggability, the device stays alive.
17. **The platform's `qrcode::encode_qr_parts_static` (finite, systematic UR parts) is gone in 1.0.0** — only the infinite fountain `encode_qr_parts` remains. Apps that need a finite, deterministic parts list (so a companion's bc-ur decoder reassembles reliably) must build it themselves with `foundation-ur`: `let n = foundation_ur::max_fragment_len(ur_type, 100, max_size); let mut e = foundation_ur::Encoder::new(); e.start(ur_type, &data, n); let parts: Vec<SharedString> = (0..data.len().div_ceil(n.max(1))).map(|_| e.next_part().to_string().to_uppercase().into()).collect();` → `ModelRc::new(VecModel::from(parts))`. Add `foundation-ur = "0.4"`.
18. **A vendored crate that declares its own `[workspace]` breaks the build** with `multiple workspace roots found in the same workspace`. Add it to the app's `[workspace] exclude` (e.g. `exclude = [".foundation-sdk", "vendor/<crate>"]`); a path dependency doesn't need to be a workspace member.
19. **`curve25519-dalek` 4 `subtle::Choice` needs an explicit `bool::from(...)`** — `Scalar::from_canonical_bytes(b).is_some().into()` inside `debug_assert!`/`assert!` fails with `E0282: type annotations needed` because `.into()`'s target isn't inferable. Use `bool::from(… .is_some())`.
20. **`std::fs` writes are `Unsupported` on device in 1.0.0 — persist via `FileBacked` at `fs::Location::AppData`.** The device std shim does **not** wire `std::fs` to a writable location: `std::fs::create_dir_all("/data/<app>")` (or any write) returns `io::ErrorKind::Unsupported` — the log line is literally `ERR <app>: cannot create data dir /data/<app>: operation not supported on this platform`, and any keystore/settings save fails. This bites apps whose vendored logic does its own `std::fs` (keystore saves, policy files, selection markers). **Fix**: add `fs = { path = ".foundation-sdk/current/lib/keyos/api/fs" }` and `file-backed = { path = ".foundation-sdk/current/lib/keyos/utils/file-backed" }`, and route each persisted file through a byte-blob store — device impl `#[cfg(target_os = "xous")]` uses `let (backing, _restored) = FileBacked::<Vec<u8>, fs_permissions::FileSystemPermissions>::new(name, fs::Location::AppData);` (the constructor returns `(Self, bool)`, the flag saying whether an existing file was restored; bind it or the tuple has no `.guard()`) (`fs::use_api!()`; `.as_slice()` to read, `*self.backing.guard() = bytes` to write atomically), host impl keeps `std::fs` under `~/.<app>/`. Keep the logic crates pure: give them blob APIs (`to_bytes`/`from_bytes`) so the app owns the store and hands it bytes — no path or `fs` dep leaks into the logic crates. If the app's engine owns persistence, give the engine a `Mutex<Blob>` in place of the `PathBuf`. Confirm on device: create an entry, kill + relaunch the app, the entry survives (proves the AppData blob round-tripped). The `os/fs` grants come from the `fs-generic` template.
21. **An SDK app requesting `GetSeed` is ALWAYS an author mistake — use `GetAppSeed`.** This is not a blocked-but-legitimate capability and not a platform gap: no SDK app has a valid reason to read the device's raw master seed. `GetAppSeed` is the correct and only seed source for a third-party app — a per-app, domain-separated 32 bytes — and any key derived from it *is* the app's real identity, not a degraded stand-in. **It is not device-bound**: as of 1.0.0 `os/security` derives it as `hmac256(app_id, master_seed)` with no device-unique material, so restoring the same BIP-39 master seed onto another Passport reproduces the same app seed for the same app-id. Two consequences, one of them conditional:

    - Unconditional: the app seed is only as private as the master seed, and any app-id change rotates it.
    - Conditional on that derivation: app-seed-rooted keys survive device loss through the ordinary seed backup. **This is current behaviour, not a committed API.** Nothing in `api/security` documents the formula or promises it is stable, so if the derivation later gains a salt, a version byte, or device-unique material, keys rooted in today's app seed become unreachable. Treat "the seed backup already covers my keys" as true for now, but note you cannot confirm it from anything the SDK ships: `api/security` carries only the client wrapper, with no rustdoc on `app_seed()`, and the derivation lives in the `os/security` server, which is not in the bundle at all. Before shipping an app that would lose user funds or identity if this changed, get the guarantee in writing from the KeyOS team rather than inferring it from the crates you have.

    If the original app lists `GetSeed` (e.g. to derive an external protocol identity from the BIP-39 master mnemonic), the *original author* misunderstood the model; **fix it in the port: drop `GetSeed` from `app-config`, keep `GetAppSeed`, and derive from the app seed** — `Mnemonic::from_entropy(app_seed_bytes)` → the same derivation path, now correctly rooted in the app seed. Do not frame this as a fallback, and do not ask for master-seed access to be opened to SDK apps. (Mechanically, `GetSeed` is also ungrouped/Foundation-only, so leaving it in the manifest gets the app denied and can crash it at launch — another reason it must come out — but the point is that it should never have been there.) QR-import of an existing external secret is unaffected and remains available.
22. **A crypto dep pins `getrandom` newer than the SDK's xous fork (0.2.10) — vendor the fork relabeled.** The `[patch.crates-io] getrandom = { path = "…/imports/getrandom" }` only overrides getrandom *at version 0.2.10* (the SDK fork's version). A dep that hard-requires a newer 0.2.x (e.g. `ecies 0.2.11` requires `getrandom ^0.2.17`) resolves to the registry getrandom, which fails on `armv7a-unknown-xous-elf` with `error: target is not supported` (no xous backend). Pinning `getrandom = "=0.2.10"` then *conflicts* (`failed to select a version … all possible versions conflict`). **Fix**: copy the SDK fork (`.foundation-sdk/current/lib/keyos/imports/getrandom`) into the app as `imports/getrandom`, bump its `version` to satisfy the requirement (e.g. `0.2.17` — the fork is 0.2.10 code plus a xous backend), fix its `xous` path dep (`../../xous/xous-rs` → `../../.foundation-sdk/current/lib/keyos/xous/xous-rs`), point `[patch.crates-io] getrandom` at `imports/getrandom`, drop any `=0.2.10` pin, and add `imports/getrandom` to `[workspace] exclude`.

    ⚠️ **The relabel is a lie to Cargo, so check it holds.** Later 0.2.x releases did add public API (`getrandom_uninit` in 0.2.12) and backend fixes, so a dep that wants `^0.2.17` for something added after 0.2.10 fails to compile against code wearing a 0.2.17 label. The fork is a path dependency built from source, so you get `` E0425: cannot find function `getrandom_uninit` in crate `getrandom` `` (or `E0432` on the import), not a link error: don't go looking at the linker. Read what the dep actually calls before trusting the version number. The app-local copy also stops tracking later fixes to the SDK fork's xous backend, so treat it as a stopgap: the durable fix is the SDK fork rebased onto a newer 0.2.x, worth raising with the KeyOS team.
23. **`prost-build`/`tonic-build` needs `protoc`, which the build env lacks — vendor it.** A crate that compiles `.proto` at build time (vendored protocol crates are the usual case) panics: `Could not find protoc. If protoc is installed, try setting the PROTOC environment variable…`. There is no `protoc` on the system or in the nix build shell. **Fix** (self-contained, no system install): add `protoc-bin-vendored = "3"` to the proto crate's `[build-dependencies]` and set the env from its bundled binary at the top of `build.rs`: `std::env::set_var("PROTOC", protoc_bin_vendored::protoc_bin_path().expect("vendored protoc"));`. Applies to the vendored crate, not the app.

    Weigh the trade-off first: `protoc-bin-vendored` ships prebuilt binaries that then execute during the build of an app that handles keys. If an opaque build-time binary is not acceptable to you, generate once and commit the output instead. Two details make that work: get a `protoc` from outside the build (`nix shell nixpkgs#protobuf`, or run the `protoc-bin-vendored` binary once yourself), and switch the consumer from `include!(concat!(env!("OUT_DIR"), "/<pkg>.rs"))` to a plain `mod`, or the generated file is still looked for in `OUT_DIR` and the build fails exactly as before. The `.proto` rarely changes, so the regeneration cost is close to zero.
24. **Fetch `app_seed()` (any permission-prompting call) on the MAIN thread, before background workers need it.** The grant prompt for a permission like `GetAppSeed` is presented against the app's gui connection; a call made from a detached `spawn_worker`/`std::thread` before `ui.run()` can't present it — the gui-server logs `permission prompt for request 0 dropped unanswered; denying` and the security blocking call panics the app (`blocking_archive.rs … unwrap on Xous(AccessDenied)`, exit 255 at launch). This bites apps that fetch the seed in a detached worker "to keep the blocking call off the UI executor", or inside a coordinator thread. **Fix**: call `Security::default().app_seed()` synchronously in `app_main` on the main thread — the brief block is just the Allow prompt — and pass the resulting `[u8; 32]` into the worker/thread. Once granted ("Allow Always"), subsequent launches don't prompt, but the main-thread fetch stays correct for first-run.

## 13. Porting an in-tree `app!` app: the compat-shim pattern

Apps written in-tree inside a KeyOS checkout (`app!` macro, `{ workspace = true }` deps, built via `cargo xtask`) import the *legacy* in-tree widget library — `BaseWindow`, `CurrentTheme`, `Palette`, `Utils`, `TR`, `Size`, `Importance`, and widgets like `AppHeader`/`BasePage`/`ScrollBody`/`QrCodeCard`/`Icon`/`TextLg` from `@ui/widgets.slint`, `@ui/theme.slint`, `@ui/i18n/i18n.slint`. None of these exist in the packaged ui2 `@ui` (which is per-component: `button.slint`, `card.slint`, … + `theme.slint`'s `Theme` global). The proven approach is a **`ui/compat/` shim**:

1. **Enumerate the exact `@ui` symbol surface first** — imports are often multi-line, so a naive `grep` under-counts, and the legacy surface spans `widgets.slint`, `theme.slint` and `i18n/i18n.slint`, so match every `@ui/` import rather than just the widgets one:

    ```sh
    perl -0777 -ne 'while(/import\s*\{([^}]*)\}\s*from\s*"[^"]*\@ui\/[^"]*"/g){print "$1\n"}' $(find ui -name '*.slint') | tr ',' '\n' | sed 's/^ *//;s/ *$//' | sort -u
    ```

    Without the file list the command reads stdin and silently returns nothing; without the wider pattern the shim misses globals like `CurrentTheme`, `Palette` and `TR`, which only surface as failures much later in the port.
2. Write `ui/compat/theme.slint` and `ui/compat/widgets.slint` that **export the legacy symbol names, implemented on ui2 + the `Theme` global** (so colors flow from your SDK theme, §6). Map the legacy `Palette`/`CurrentTheme`/brand tokens to `Theme.palette-*` and `Theme.is-dark`; reimplement the widgets over ui2 (`Icon`→resolve `Images.image(name)`, `IconButton`/`Spinner`/`Input` wrap the ui2 equivalents, `BaseWindow`/`BasePage`/`AppHeader`/`ScrollBody` are thin layouts). Read the legacy bodies from a KeyOS checkout's `ui/ui/` to match public APIs.
3. **Remap every app import** `@ui/...` → `compat/...` (relative depth per file: `compat/…` from `ui/`, `../../compat/…` from `ui/pages/<n>/`).
4. **Vendor the named icon SVGs the app references into `resources/images/`.** The compat `Icon`/`IconButton` resolve `Images.image(name)` → `resources/images/<name>.svg`; the in-tree `@ui` supplied these natively but packaged ui2 does **not**, so any unresolved name renders as a *blank glyph* (back chevron, menu ellipsis, hero icons all invisible) with a runtime log `Could not load image "images/<name>"` — it does not fail the build, so it's easy to miss until you look at the device. Enumerate every referenced name — `grep -rhoE '(icon|name|inner-icon|outer-icon): "[a-z0-9-]+"' ui/ | grep -oE '"[a-z0-9-]+"' | sort -u` — and copy each `<name>.svg` from a KeyOS checkout's **`ui/ui/icons/`** (24×24, single-color; the compat `Icon` colorizes them). Hand-author any app-specific glyph (matching the app's launcher icon works well).
5. `app.slint` becomes `inherits Window { Router { } }` (drop the legacy `BaseWindow` shell); keep `include_router`/`include_translations` in `build.rs`; wire i18n (gotcha 14) and any native `Utils` callbacks (e.g. `Utils.qrcode` → `slint_keyos_platform::qrcode::render`) in Rust.

This keeps the page/router sources almost untouched — only their import lines change — while re-skinning the whole app onto ui2 and your SDK theme.

## 14. Porting an app whose OS surface is missing: the feature-gate + mock pattern

Some apps depend on an OS surface the packaged 1.0.0 SDK does not ship — the clearest case is the USB vendor-interface transport (`usb` crate / `os/usbdev` server), used by apps that talk to a browser extension or host CLI. `foundation build` (device target) can't resolve the dep, so the transport is unbuildable. Rather than block the whole port, ship a **mock transport now** and preserve the real one for when the API lands:

1. **Isolate the transport.** These apps usually already gate it — `cfg(not(keyos))` = a host WebSocket dev transport, `cfg(keyos)` = the device transport. Keep both files.
2. **Feature-gate the real device transport** behind a cargo feature and add a mock alongside it:
   ```rust
   // transport.rs
   #[cfg(all(keyos, feature = "usb"))]  mod webusb;  #[cfg(all(keyos, feature = "usb"))]  pub use webusb::serve;
   #[cfg(all(keyos, not(feature = "usb")))] mod mock; #[cfg(all(keyos, not(feature = "usb")))] pub use mock::serve;
   ```
3. **Do NOT declare the unresolvable path dependency yet** — Cargo errors on a missing path even when optional. Add only a marker `[features] usb = []`; when the SDK ships the API, change it to `usb = ["dep:usb"]` and add the (now-resolvable) dep. The real transport file stays in the tree, written against the intended API, but is only compiled under `--features usb`.
4. **The mock** matches the real entry point's signature, sets a status line, and returns — the app launches and its local UI is fully usable (only the host bridge is absent):
   ```rust
   pub async fn serve(_engine: Arc<Engine>, _bind: &str) -> anyhow::Result<()> {
       super::set_status("USB bridge unavailable on this SDK — app usable locally");
       Ok(())
   }
   ```
5. **Drop the corresponding permission grants** from `app-config.toml` (the mock uses no USB; granting an absent server's messages fails — and ungrouped messages would crash the app anyway, §7.3).
6. **Report the missing surface to the KeyOS/SDK team** and reference that report in the mock's status message and code comments, so the finish-line work is discoverable.

The same pattern generalizes to any OS surface the app cannot actually use, whether it is absent or merely out of reach. **Treat `bt` as absent**: the SDK's internal `bt` package is only a `BluetoothError` compatibility placeholder for QuantumLink v1, so direct uses of `BluetoothApi`, `SubscribeBle`, or `SendBle` do not compile. **`quantum-link` is the second kind**: the crate ships, but its Envoy-sync messages are grouped under `network-and-pairing.wallet-sync` and overridden with `requiredSignature = "foundation"`; a third-party app is limited to its grantable status surface. For a Bluetooth transport, apply this section without adding a real `bt` dependency or `os/bt` grants. For QuantumLink, keep only grouped grants the app can hold (such as `network-and-pairing.status-and-rates`) and stub calls to Foundation-only messages. Escalating the missing surface still differs by route: Bluetooth needs a supported public SDK API, while QuantumLink needs the `requiredSignature = "foundation"` restriction lifted on the already-grouped messages. When the transport is not a separable `serve()` but a set of APIs called throughout the app, invert it: provide a feature-gated module of **no-op stand-ins for the exact symbols the app uses** — with subscription streams that never yield and sends that succeed silently — so the transport logic compiles and runs unchanged as no-ops, and the rest of the app (UI, key derivation, local flows) stays fully exercised on device. If the mock feeds a QR/UR encoder, return a non-empty placeholder (fountain encoders panic on empty input).

When the API lands: add the dep, build with the feature, restore the permissions — and the preserved transport finishes the app end-to-end with no UI/logic rework.
